## 1. RAM LRU patch 能否套用 / mainline 有無等價
- patch 僅 2 檔（hpp +5、cpp +65）。`git apply --check` 直接失敗（context 漂移），`--3way`：hpp 乾淨；cpp 有 **1 處衝突**（expert_source.cpp ~:3339-3350，reserve_exchanges 附近的 `STRATA_EXCHANGE_ROTATE` 判斷），另兩處（pin_cache_complement 初始化、blob_stable 前新函式）乾淨。呼叫點 `expert_pool_dispatch_multi` 的 `pt("ran")` 前仍在，但前面新增 `d.peer->finish` 區塊（多 GPU），語意無衝突。手動解衝突工時約 0.5–1 小時；風險在於 `d.host_res`/`job_of`/`jobs_multi` 欄位語意是否被 mainline 的 cache/cpu PR 改動（需讀碼確認，未驗證）。
- 等價功能：**有，但機制不同**。`STRATA_RAM_ADAPT=<n>`（opt-in，--serve，單 GPU，需 `--adapt-every`；generate.cpp ~14268、`FileExpertSource::replace_resident` expert_source.cpp ~3469）：視窗之間依 adaptive tier 的衰減使用量，把「近期常被路由（≥2）但不在 RAM 副本」的 expert 換進同層「未使用（<0.5）」expert 的 RAM 位置，每層一對、每次最多 n 個；**從檔案（SSD）讀一個 blob** 且在主執行緒做。與我們的差異：我們的 LRU 在 CPU job 已經讀到 blob 後直接 memcpy 進 RAM 副本（零額外 SSD 讀），以「同層 LRU」選 victim；mainline 要額外讀檔、在視窗間、依使用量門檻。兩者互斥性：RAM_ADAPT 在 `STRATA_EXCHANGE_ROTATE=1`、layer split、peer、`--batch` 下無作用；我們的 LRU 則排除 exchange rotation。兩者可否同時開未驗證（建議不同時開）。
- mainline 自報數字（docs/DETAILS.md ~L172-190，RTX 3060 12GB、32GB RAM、Linux、IQ2_XS、`--adapt-async 1 --spec 3`、對 v0.1.43，47 個真實請求重播）：decode 43.26 -> 50.40 tok/s（+16.5%），decode 檔案層讀取/token 14.15 -> 2.67（含促進讀取 3.16）。注意：該場景 file tier 約 6000 experts、遠比我們嚴重（我們 RAM-tier miss 僅 ~2–3%），所以我們可期待的絕對增益遠小；單機單量化、作者自測。
- 我們的 tie-order 小改善（untouched slot 依 profile rank 而非最小 expert id）：RAM_ADAPT 以使用量選 `out`（最小 u），本質上已用使用量排序，不需另做。
